# Failure cases (L5)

Each case has a test that reproduces it, the outcome observed, and the rule that handles it. Tests run in
`tests/Sync.Tests` (`make test`) against real SQL Server 2022 with AdventureWorks restored fresh per test,
PostgreSQL 17 and RabbitMQ 4 in Testcontainers. Test names are abbreviated; search the class.

| # | Case | Test (class) | Observed outcome | Rule |
|---|---|---|---|---|
| 1 | **Duplicate delivery**, new side | `Duplicate_delivery_changes_nothing`, `Concurrent_delivery_of_the_same_message_applies_it_once` (`WorkOrderSyncHandlerTests`) | A redelivered id is skipped even with a different body; four concurrent copies give 1 applied, 3 duplicates | The inbox row (`processed_message`) commits with the change; a unique violation from a racing copy counts as a duplicate |
| 1b | Duplicate delivery, legacy side | `Duplicate_command_is_applied_once`, `Concurrent_duplicates_apply_once` (`LegacyCommandHandlerTests`) | One order created, one inbox row | `sync.Inbox` insert, session markers and procedure call share one transaction |
| 2 | **Out of order** | `Out_of_order_older_version_is_ignored…` (`WorkOrderSyncHandlerTests`); `Shuffled_and_duplicated_delivery_converges…` (`ConvergenceTests`); `Scrap_commands_give_the_same_total_in_either_order` | An older version arriving late is recorded and ignored. 25 random shuffles of a full order history, each message delivered 1–3 times, always end equal to the legacy tables (quantity, scrap, due date, closed, every operation's actuals) | Whole-order snapshots with a per-order version: the newest wins whatever the arrival order. Commands that must add up (scrap) travel as deltas, so order does not matter |
| 3 | **Both sides edit the same order** (policy and detection added in L6; see [conflicts-and-reconciliation.md](conflicts-and-reconciliation.md)) | `Scrap_entered_on_both_sides_adds_up`; `Both_sides_editing_the_due_date…`; `Legacy_truth_replaces_the_optimistic_local_state`; `Crossing_edits_of_the_due_date_are_logged…` (`ReconciliationTests`) | Scrap from both sides adds up (3 + 2 = 5). For the same field the later write wins on the legacy side, and the outbox shows `new, legacy, new` origins, so the overwrite is visible. After the confirmation arrives the new side shows the legacy value | Scrap: delta, never a conflict. Due date and quantity: the planner wins, and each side logs what it overwrote or held back; after everything crosses, both sides are equal |
| 4 | **Broker down** | `Broker_down_loses_nothing…` | With RabbitMQ stopped, desktop edits continue; the relay throws and both rows stay unpublished. After restart the same relay and consumer connections recover, the rows publish in order, and PostgreSQL ends with scrap 3 and exactly 3 processed messages (create + 2 scraps). New side: `New_side_relay_leaves_commands_unpublished…` | The change and its outbox row commit together, so the broker is never on the write path. Publish first, mark published after (at-least-once). Changing that order loses a row: checked by mutation |
| 5 | **Consumer crashes mid-message** | `A_consumer_that_dies_after_committing_but_before_acking…` | A consumer commits the change and its connection is aborted before the ack. The broker redelivers; the handler answers Duplicate; one order, one inbox row, queue drains | Ack only after the commit; redelivery is absorbed by the inbox |
| 6 | **Poison message** | `A_poison_message_is_retried_then_lands_in_the_dead_letter_queue…`; `A_message_that_fails_once_succeeds_on_retry…` | A message that always fails is delivered exactly 3 times (`MaxAttempts`), then sits in `newside.workorders.dlq` with `x-attempt = 3` and `x-error` holding the exception. A transient failure succeeds on the retry and is applied once | A failing handler publishes the message to `<queue>.retry` (TTL `RetryDelay`, then back to the main queue), up to `MaxAttempts`; then to the dead-letter queue, with the error in a header. Retries reorder messages, which cases 2 and 3 already tolerate |
| 7 | **AdventureWorks trigger rolls back** | `Trigger_rollback_fails_the_whole_command…` (`LegacyCommandHandlerTests`); `A_trigger_rollback_on_the_legacy_side_retries_then_dead_letters…` | With Microsoft's `uWorkOrder` as shipped, a quantity change raises error **3609** ("transaction ended in the trigger"; the real error 515 is only printed). Nothing is left behind: quantity unchanged, no audit row, no outbox row, **no inbox row**, so a retry is possible. Through the bus it is retried 3 times and dead-lettered in `legacy.commands.dlq` | The inbox insert is inside the same transaction as the procedure call, so a rollback undoes the inbox row too. A permanently failing command ends in the dead-letter queue instead of looping |
| 8 | **A user on the desktop app mid-migration** | `The_origin_marker_does_not_leak…`; `Scrap_entered_on_both_sides_adds_up`; `A_command_for_an_order_closed_meanwhile_is_refused…` | The desktop's writes are stamped `legacy` and the sync's `new`, even on the same pooled connection. Closing an order on the desktop while a scrap command is in flight: since L6 the command is refused, logged as a conflict (legacy wins) and answered with the order's current state; it is not retried or dead-lettered (`An_edit_of_an_order_closed_meanwhile…`) | Origin comes from `SESSION_CONTEXT`, set per command. See *Notes* for the connection-pool detail |

## Notes and limits

- **Marker clearing.** `LegacyCommandHandler` clears the session markers after each command. The leak test
  also passes with that code disabled: SQL Server's own connection-pool reset already clears
  `SESSION_CONTEXT`. The explicit clear is kept as a guard; the test checks the behaviour, not that code.
- **Dead-lettered commands.** The new side keeps the planner's optimistic value until the message is re-driven.
  The reconciliation report shows it as *dead-lettered*, and `make redrive` puts it back (proved in
  `A_dead_lettered_command_is_reported_as_such_and_redriving_it_after_the_fix…`). There is no alerting.
- The lab patch `V006` is what lets cases 3 and the happy path change a quantity at all; case 7 runs without it.
- Fault injection is "stop or abort the container/connection". Network partitions and slow brokers are not simulated.
